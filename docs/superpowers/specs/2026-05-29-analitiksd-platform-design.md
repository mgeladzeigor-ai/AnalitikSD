# AnalitikSD — система отчётности по данным компании (дизайн)

**Дата:** 2026-05-29
**Статус:** дизайн утверждён, ожидает ревью спеки
**Этот документ описывает MVP первого под-проекта.** Полная платформа разбита на под-проекты (см. раздел «Декомпозиция»).

## 1. Проблема и цель

В компании три основные системы-источника данных:

- **Битрикс24** — информация о компании, задачи, люди, CRM.
- **УТ (1С Управление Торговлей)** — коммерческая часть: заказы, отгрузки, закупки. Доступ через SQL.
- **СД (Сервис-Деск)** — обращения и наряды на работу. Самописная система, доступ напрямую к её БД (SQL, диалект уточняется).

Нужна система, которая умеет: зайти в любой из источников, вытащить нужный срез данных, построить отчёт или ответить на вопрос на естественном языке. Доступ — через веб-приложение с авторизацией и разграничением прав. Должна быть возможность подключать разные LLM-модели. Построенный отчёт можно сохранить — он становится постоянным, и его можно в любой момент открыть и «обновить данные» (та же логика, свежие данные).

## 2. Ключевые решения (зафиксированы при брейнсторминге)

| Тема | Решение |
|------|---------|
| Доступ к данным | Гибрид: MCP там, где есть (Битрикс, финансы/УТ), прямые SQL-коннекторы там, где нужно (СД, спец-запросы) |
| Логика отчётов | Гибрид: агент строит ad-hoc → «сохранить» фиксирует детерминированный «рецепт» |
| Обновление сохранённого отчёта | Детерминированно: повтор того же рецепта без LLM, только свежие данные |
| LLM-модели | Провайдер-абстракция (любые модели). Жёсткого запрета на облако нет → старт на облачном API |
| Агентный слой | Claude Agent SDK (нативный MCP, быстрый старт); мульти-модельность за интерфейсом провайдера — позже |
| Права доступа | По источникам + по отчётам на ролях. Row-level — позже (заложено в архитектуру) |
| Авторизация | Своя (сессия/JWT) с ролями, архитектурно готова к SSO/Битрикс |
| Развёртывание | Облако, ~50 пользователей. Нужен защищённый шлюз к внутренним БД (вне MVP) |

## 3. Декомпозиция платформы на под-проекты

1. **Ядро + коннекторный слой** — единый интерфейс «источник данных».
2. **AI-движок отчётов** — вопрос → план запросов → данные → ответ/таблица; сохранение рецепта.
3. **Сохранённые отчёты + обновление** — хранение рецептов, детерминированное обновление.
4. **Веб-приложение + авторизация.**
5. **Модуль прав доступа (RBAC).**
6. **Расширение источников** — УТ, СД, новые MCP/SQL + защищённый шлюз к внутренним БД.
7. **Мульти-модельность + локальные модели.**

### MVP (этот документ) — вертикальный срез

Веб-приложение с входом → вопрос → агент ходит в **один источник (Битрикс через MCP)** → строит ответ/таблицу → можно **сохранить отчёт** и **обновить** его. Минимальный RBAC (источники + отчёты на ролях). Одна облачная модель. SQL-источники (УТ, СД) подключаются позже — сначала разворачиваем и тестируем на Битриксе.

## 4. Архитектура и компоненты (MVP)

```
┌─────────────┐     HTTPS      ┌──────────────────────────────────────┐
│   Браузер   │ ◄────────────► │            FastAPI (Python)          │
│  React SPA  │                │                                      │
└─────────────┘                │  ┌────────────┐   ┌───────────────┐  │
                               │  │ Auth/RBAC  │   │ Report Service│  │
                               │  └────────────┘   └──────┬────────┘  │
                               │  ┌────────────────────┐  │           │
                               │  │  Agent Service     │◄─┘           │
                               │  │ (Claude Agent SDK) │              │
                               │  │  + ModelProvider   │              │
                               │  └─────────┬──────────┘              │
                               └────────────┼─────────────────────────┘
                                            │ MCP
                                   ┌────────▼─────────┐   ┌─────────────┐
                                   │ Bitrix24 MCP     │   │ PostgreSQL  │
                                   │ (уже подключён)  │   │ users/roles │
                                   └──────────────────┘   │ reports/runs│
                                                          └─────────────┘
```

**Компоненты:**

- **React SPA** — вход, окно вопроса/чата, просмотр результата (таблица), список сохранённых отчётов, кнопка «Обновить».
- **Auth/RBAC** — своя авторизация (сессия/JWT), роли; проверка доступа к источникам и отчётам.
- **Agent Service** — обёртка над Claude Agent SDK; принимает вопрос, через MCP ходит в Битрикс, возвращает результат + структурированный план выполнения (рецепт). `ModelProvider` — тонкий интерфейс (сейчас одна реализация — Anthropic), задел под мульти-модельность.
- **Report Service** — сохранение рецепта, детерминированное обновление (исполнение рецепта без LLM), история запусков.
- **PostgreSQL** — пользователи, роли, права, определения отчётов (рецепты), история запусков.
- **Bitrix24 MCP** — единственный источник данных в MVP.

Внутренние SQL-базы (УТ, СД) и защищённый шлюз — вне MVP (под-проект 6).

**Принцип проектирования:** каждый слой имеет одну ответственность и общается через явный интерфейс. Источники данных за единым интерфейсом `DataSource`, модели — за `ModelProvider`. Это позволяет добавлять SQL-источники и новые модели, не трогая остальное.

## 5. Поток данных (ядро системы)

**Поток 1: Ad-hoc вопрос (с участием LLM)**

1. Пользователь вводит вопрос («сколько сделок закрыто в мае по каждому менеджеру»).
2. Agent Service проверяет права (какие источники доступны роли).
3. Claude Agent SDK через MCP делает серию вызовов к Битриксу (напр. `crm_deal_list` с фильтрами), возможно в несколько шагов.
4. Агент **строит декларативный конвейер** (вызовы + трансформации + представление), движок его **исполняет** — результат таблицы получается исполнением конвейера, а не «пересказом» LLM.
5. Вместе с результатом сохраняется структурированный план (рецепт): список вызовов инструментов, шаги трансформации, вид представления.
6. Результат показывается пользователю (LLM может добавить текстовое пояснение, но цифры — из конвейера).

**Поток 2: Сохранение отчёта**

7. Пользователь жмёт «Сохранить» → рецепт из шага 5 пишется в БД + название + параметры (период и т.п.).

**Поток 3: Обновление (без LLM — детерминированно)**

8. Пользователь открывает сохранённый отчёт, жмёт «Обновить».
9. Report Service берёт рецепт и повторяет ровно те же вызовы MCP (с теми же или обновлёнными параметрами периода).
10. Применяет те же шаги трансформации (код, не LLM).
11. Показывает свежие данные. LLM не участвует.

**Ключевой принцип:** рецепт — это декларативный конвейер `[вызовы источника] → [трансформации] → [представление]`. Агент при построении сериализует свой план в этот формат; движок исполняет. Обновление — исполнение конвейера движком без LLM. Это даёт воспроизводимость, скорость и предсказуемость.

### Гарантии надёжности (результат проверки подхода)

1. **То, что видит пользователь = результат конвейера**, а не текст от LLM. Агент собирает конвейер, движок его исполняет, и именно этот результат показывается и сохраняется. LLM только поясняет. Это полностью снимает риск рассинхрона «показанного» и «обновлённого».
2. **Не каждый вопрос выразим в рецепте.** Если агент не может выразить отчёт в DSL — он отвечает как ad-hoc (разово), кнопку «Сохранить» не предлагает, с пометкой «этот отчёт пока нельзя сделать обновляемым». Честнее, чем сохранить нерабочий рецепт.
3. **Детерминизм движка:** полная пагинация всех страниц источника; явная сортировка в рецепте для стабильного порядка строк; «свежие данные, та же логика» = одинаковые запросы при новых данных; будущие SQL-источники — только параметризованные запросы; при дрейфе схемы запуск падает с понятной ошибкой и кнопкой «пересобрать».

## 6. Модель данных

**Таблицы PostgreSQL:**

```
users          (id, email, password_hash, name, is_active, created_at)
roles          (id, name)                          -- напр. admin, analyst, viewer
user_roles     (user_id, role_id)
data_sources   (id, key, type[mcp|sql], config)    -- реестр источников; MVP: bitrix(mcp)
role_sources   (role_id, source_id)                -- RBAC: какие источники доступны роли
reports        (id, name, description, owner_id, recipe jsonb, params jsonb,
                is_refreshable bool, created_at, updated_at)
report_perms   (report_id, role_id, access[view|edit])  -- RBAC: по отчётам
report_runs    (id, report_id, started_at, finished_at, status[ok|error],
                row_count, result jsonb|ref, error, triggered_by)
```

**Формат рецепта (`reports.recipe`, jsonb):**

```json
{
  "version": 1,
  "source": "bitrix",
  "steps": [
    { "type": "tool_call", "tool": "crm_deal_list",
      "params": { "filter": { ">=CLOSEDATE": "{{period.from}}",
                              "<=CLOSEDATE": "{{period.to}}",
                              "CLOSED": "Y" },
                  "select": ["ID","ASSIGNED_BY_ID","OPPORTUNITY"] } }
  ],
  "transform": [
    { "op": "group_by", "keys": ["ASSIGNED_BY_ID"] },
    { "op": "aggregate", "metrics": [
        { "fn": "count", "as": "deals" },
        { "fn": "sum", "field": "OPPORTUNITY", "as": "amount" } ] }
  ],
  "presentation": {
    "type": "table",
    "columns": ["ASSIGNED_BY_ID","deals","amount"],
    "sort": [{ "by": "amount", "dir": "desc" }]
  }
}
```

**Параметры (`reports.params`)** — то, что можно менять при обновлении без LLM:

```json
{ "period": { "type": "date_range", "default": { "from": "2026-05-01", "to": "2026-05-31" } } }
```

`{{period.from}}` в рецепте — плейсхолдеры, которые движок подставляет из `params` при каждом запуске. «Обновить за новый период» = поменять параметр, рецепт тот же.

**Поддерживаемые операции трансформации (MVP):** `filter`, `group_by`, `aggregate` (`count`/`sum`/`avg`/`min`/`max`), `sort`, `computed` (вычисляемая колонка), `limit`.

**Результаты запусков** (`report_runs.result`) кэшируются: открыл сохранённый отчёт — видишь последний результат мгновенно; «Обновить» запускает новый run.

## 7. Обработка ошибок

Принцип: ошибки не «глотаем» — каждая видна пользователю и пишется в `report_runs`.

1. **Ошибки источника (MCP/Битрикс):** недоступен / таймаут / rate-limit → `status=error`, текст сохранён, пользователю «Источник недоступен». Прошлый кэшированный результат не затирается неудачным запуском. Ретраи с экспоненциальной задержкой на сетевые/rate-limit ошибки (не на логические).
2. **Ошибки агента (ad-hoc построение):** не понял вопрос / нет данных → честный ответ «не могу построить, уточните…», без выдуманных цифр. Превышен бюджет шагов/токенов → стоп с сообщением, без бесконечного цикла.
3. **Ошибки рецепта при обновлении (дрейф схемы):** поле/инструмент изменились → `status=error` + «структура источника изменилась, пересоберите» + кнопка «пересобрать через LLM».
4. **Ошибки прав доступа:** нет доступа к источнику/отчёту → 403, явное сообщение, попытка логируется.
5. **Ошибки авторизации:** невалидная/просроченная сессия → 401, редирект на вход.
6. **Валидация параметров:** кривой период/фильтр → 400 с понятным текстом до обращения к источнику.

**Сквозные правила:**

- Каждый запуск отчёта = запись в `report_runs` со статусом и (при ошибке) текстом — аудит и история.
- Никаких «тихих» fallback-ов с пустыми/выдуманными данными: пустой результат и ошибка — **разные** состояния, показываются по-разному.
- Секреты (ключи моделей, доступы к источникам) — в переменных окружения / секрет-хранилище, не в БД открытым текстом и не в логах.

## 8. Тестирование

Принцип: ядро (рецепт-движок и RBAC) — тщательно (TDD); LLM-часть — на моках.

1. **Движок трансформаций (юнит, важнейшее):** каждая операция на фиксированных данных → точный результат; подстановка плейсхолдеров; пагинация (мок на 3 страницы → все строки); детерминизм (один рецепт + одни данные → одинаковый результат дважды).
2. **RBAC (юнит/интеграционные):** роль без доступа к источнику → 403; роль без доступа к отчёту его не видит; табличные тесты матрицы «роль × источник», «роль × отчёт».
3. **Сохранение/обновление (интеграционные):** ad-hoc → сохранил → обновил → логика совпадает, данные свежие; обновление **не вызывает LLM** (мок провайдера со счётчиком вызовов).
4. **Agent Service (на моках MCP):** мок Битрикс-MCP с детерминированными ответами → агент строит валидный рецепт по схеме; не-выразимый вопрос → отчёт помечается как ad-hoc (без «Сохранить»). Реальные вызовы к Битриксу — отдельные smoke-тесты, не в основном прогоне.
5. **Auth (интеграционные):** логин/логаут, истёкшая сессия → 401, неверный пароль, неактивный пользователь.
6. **E2E (минимум):** вход → вопрос → результат → сохранить → обновить → выход.

**Подход к разработке:** ядро (движок, RBAC) — через TDD. UI и интеграции с LLM — тесты после, на моках. Реальные внешние системы — только smoke-тесты.

## 9. Технологический стек

- **Backend:** Python + FastAPI.
- **Агент:** Claude Agent SDK (нативный MCP) за интерфейсом `ModelProvider`.
- **Frontend:** React (SPA).
- **БД:** PostgreSQL.
- **Авторизация:** своя (сессия/JWT) + роли.
- **Развёртывание:** облако (~50 пользователей).
